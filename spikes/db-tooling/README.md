# ADR-0014 database tooling spike (throwaway)

Validation code for [ADR-0014](../../docs/DECISIONS/0014-database-tooling.md). Not application code and not the M1 schema. Results: [`docs/SPIKE_DB_TOOLING_REPORT.md`](../../docs/SPIKE_DB_TOOLING_REPORT.md).

## Requirements

- Node.js 26.13.0 (`.nvmrc`) and pnpm 12.16.1 (`packageManager`)
- A Docker engine (validated with Colima 0.10.3, Docker Engine 29.5.2)
- Port `127.0.0.1:54329` free

## Run

```sh
cd spikes/db-tooling
nvm use
pnpm install --frozen-lockfile
pnpm spike                      # everything, from a fresh database
SKIP_INSTALL_CHECK=1 pnpm spike # skip the arm64/amd64 container install builds
```

Individual steps: `pnpm db:reset`, `pnpm typecheck`, `pnpm db:types:check`, `pnpm test`, `bash scripts/install-check.sh`.

Clean up: `docker compose down --volumes`.

## Transaction wrapper contract

These rules are the accepted ADR-0014 architecture, implemented in `src/db.ts` and tested in `tests/04-kysely-transactions.test.ts`.

- One centrally managed `pg.Pool` and one centrally managed root Kysely instance.
- The module owns `BEGIN` / `COMMIT` / `ROLLBACK`. Handlers receive only a Kysely `Transaction`.
- Nested `transaction()`, `startTransaction()`, and `connection()` are rejected at compile time and at runtime.
- A handle used after commit or rollback throws (`Transaction is already committed` / `already rolled back`) and cannot read another tenant after the connection is reused.
- Tenant context is set with `set_config(..., true)` as the first statement of `withTenant`. Missing context denies access.
- If a database statement fails, the wrapper fails even when the handler catches the error. After the handler returns, a probe query detects PostgreSQL SQLSTATE `25P02` and throws `TransactionAbortedError`, so a swallowed error cannot look like success (PostgreSQL would otherwise turn `COMMIT` of an aborted transaction into a silent `ROLLBACK`).
